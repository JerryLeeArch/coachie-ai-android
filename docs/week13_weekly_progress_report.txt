현재 상태: 로컬 구현 초안, GitHub 미반영

주의 사항:
이 문서는 13주차 진행보고서 작성을 위해 미리 정리한 초안이다. 현재 구현 내용은 로컬 작업 상태이며 아직 GitHub에 커밋/푸시하지 않았다. 제출 전에는 13주차 커밋 수, 커밋 해시, 커밋 히스토리 그래프, 주요 화면 스크린샷을 다시 업데이트해야 한다.


2. 13주차 개발 목표

13주차의 핵심 목표는 12주차에 구현한 식단 저장/수정/조회 흐름을 더 실제 사용에 가깝게 다듬고, 목표 설정 기능을 단순 입력값이 아니라 사용자별·시점별로 추적 가능한 데이터 구조로 확장하는 것이다. 또한 사용자가 인바디에서 확인할 수 있는 신체 측정값을 앱 안에 날짜별로 기록하고, 해당 값을 목표 설정과 AI Nutrition Plan 계산에 활용할 수 있도록 개선하였다.

12주차까지는 목표 칼로리와 단백질 목표가 AIDietNavHost의 rememberSaveable 상태에 저장되어 있었기 때문에 앱을 재실행하거나 목표를 중간에 바꾸면 과거 날짜에 어떤 목표가 적용되었는지 추적하기 어려웠다. 13주차에는 목표 설정 값을 Room DB에 저장하고, 사용자가 목표를 수정할 때 기존 목표를 덮어쓰지 않고 새로운 기간의 목표 계획으로 저장하도록 구조를 변경하였다.

주요 목표는 다음과 같다.

- Edit Meal 화면에서 AI가 분석한 kcal 및 영양소 값을 사용자가 직접 수정 가능하게 구현
- 목표 설정 화면에서 현재 체중은 필수 입력, 골격근량과 체지방률은 선택 입력으로 구분
- 목표 설정 화면에서 사용자가 원할 때 현재 몸 상태를 별도 입력할 수 있는 Body Status 입력 기능 추가
- 인바디 측정값인 체중, 기초대사량, 골격근량, 체지방량, 체지방률을 날짜별로 저장할 수 있도록 DB 확장
- 목표 기간 입력 충돌을 방지하기 위해 Target Date 또는 Duration Weeks 중 하나만 선택하도록 UI 정리
- AI Nutrition Plan을 기본 daily target source로 사용하고, 필요할 때만 Manual Override로 직접 수정 가능하게 변경
- 이미 목표가 있는 경우 Goals 화면에서 새 입력 폼보다 현재 목표 진행 상태를 먼저 보여주는 흐름으로 개선
- 목표 편집 시 AI가 비어 있는 신체 구성 값을 추정하여 전체 목표안을 제안하고, 사용자가 Confirm해야 저장되도록 변경
- 사용자별·시점별 목표 DB 설계 및 Room Entity, DAO, Repository 추가
- 목표 수정 시 기존 목표 기간을 닫고 새 목표 계획을 insert하는 방식으로 목표 변경 이력 관리
- Home 화면이 DB의 active goal을 기준으로 칼로리/탄단지/건강 지표 목표를 표시하도록 연결
- Insights 화면에서 날짜별 실제 섭취량과 해당 날짜에 적용되던 목표를 라인 그래프로 비교하여 표시


3. 이번 주 현재까지 구현된 전체 기능

현재까지 13주차용으로 구현한 기능은 다음과 같다.

- Edit Meal 화면에서 음식 항목별 Calories, Carbs, Protein, Fat, Fiber, Sugar, Sodium 직접 수정 가능
- 기존 식단 기록을 수정할 때 저장된 영양소 값이 edit 화면 입력 필드에 자동으로 채워짐
- 사용자가 수정한 영양소 값이 MealFoodDraft로 전달되어 AI 추정값보다 우선 저장됨
- Goal Settings 화면에 Goal Period 섹션 추가
- Start Date는 기본값을 설정일로 두고, 수정 가능하지만 빈칸으로 저장할 수 없도록 검증
- 기간 설정 방식은 Target Date 모드와 Duration 모드 중 하나만 선택하도록 변경
- Target Date 모드에서는 목표 날짜를 직접 입력하고 기간은 계산값으로 표시
- Duration 모드에서는 주 단위 기간을 입력하고 목표 날짜는 자동 계산
- Current Profile에서 현재 체중은 필수 입력, 현재 골격근량, 기초대사량, 체지방률은 선택 입력으로 구현

- Body Status 입력 폼에서 측정일, 체중, 기초대사량, 골격근량, 체지방량, 체지방률 입력 가능
- Body Status 입력값은 하나 이상만 작성해도 저장 가능하도록 검증
- 체중과 체지방량이 함께 입력되면 체지방률을 자동 계산하여 목표 초안에 반영
- 저장된 최신 Body Status를 Current Profile에 불러오는 Use Latest Body Status 버튼 추가

- AI Nutrition Plan에서 하루 목표 칼로리, 탄수화물, 단백질, 지방, 식이섬유, 당, 나트륨 계산

4. 화면별 구현 내용

4.1 Edit Meal 화면

12주차에는 식단 상세 화면에서 editMeal route로 이동하고, AddMealScreen을 재사용하여 음식명, 설명, 이미지 URI를 수정할 수 있었다. 13주차에는 여기서 더 나아가 AI가 계산한 kcal 및 각종 nutrition 값을 사용자가 직접 수정할 수 있도록 변경하였다.

구현 기술:
- AddMealScreen의 FoodDraftUiState에 calories, carbsGram, proteinGram, fatGram, fiberGram, sugarGram, sodiumMilligram 상태 추가
- initialMeal이 있을 때 MealFoodRecord의 기존 영양소 값을 문자열 입력 상태로 변환
- edit 모드일 때만 Nutrition Details 영역 표시
- 숫자 키보드와 숫자 입력 필터를 적용하여 잘못된 문자 입력 방지
- FoodDraftUiState.toMealFoodDraft()에서 사용자가 입력한 값을 nullable Int로 변환

구현된 내용:
- Calories (kcal) 직접 수정
- Carbs (g) 직접 수정
- Protein (g) 직접 수정
- Fat (g) 직접 수정
- Fiber (g) 직접 수정
- Sugar (g) 직접 수정
- Sodium (mg) 직접 수정

문제 해결 과정:
AI 분석 결과는 추정값이기 때문에 사용자가 실제 음식량이나 포장지 영양성분표를 알고 있을 때 직접 수정할 수 있어야 한다. 기존 구조에서는 MealFoodDraft에 영양소 nullable 값이 이미 존재했고 MealReviewRepository에서 draft 값이 있으면 AI 분석값보다 우선 사용하고 있었다. 따라서 데이터 흐름을 새로 만들기보다는 edit 화면에서 해당 값들을 입력할 수 있도록 UI 상태만 확장하여 기존 저장 흐름을 재사용하였다.


4.2 Goal Settings 화면

Goal Settings 화면은 13주차에서 가장 크게 확장된 화면이다. 12주차에는 현재 체중, 목표 체중, 목표 기간, 목표 칼로리, 단백질 목표를 단순 입력하는 구조였지만, 13주차에는 목표 기간, 현재 신체 정보, 목표 신체 정보, AI 일일 영양 계획, Manual Override까지 포함하는 구조로 변경하였다. 추가로 사용자가 인바디 측정값을 확인한 뒤 앱에서 바로 현재 몸 상태를 입력하고, 그 값을 목표 설정 초안에 반영할 수 있도록 Body Status 입력 흐름을 추가하였다.

이후 Goals 화면의 기본 진입 흐름도 개선하였다. 이미 active goal이 있는 사용자가 Goals 화면에 들어오면 곧바로 편집 폼을 보여주는 대신, 현재 목표 기간 진행률, Body Progress, Daily Targets를 먼저 보여준다. 사용자는 이 화면에서 현재 Body Status를 바로 입력할 수 있고, 필요할 때만 Edit Goal 버튼을 눌러 목표 편집 폼으로 들어간다.

목표 저장 방식도 즉시 저장이 아니라 AI proposal 확인 방식으로 변경하였다. 사용자가 목표 편집 폼에서 Generate AI Goal Proposal을 누르면 AI가 비어 있는 골격근량, 체지방률, 목표 체중 같은 값을 추정하여 전체 목표안을 만든다. 이 제안은 AI Goal Proposal 카드에 표시되고, 사용자가 Confirm Goal을 눌러야 실제 goal_plans에 저장된다.

구현 기술:
- Start Date와 Target Date는 LocalDate.parse로 검증
- Duration 모드에서는 시작 날짜와 주 단위 기간을 바탕으로 목표 날짜 자동 계산
- parseGoalDateRange 함수로 validFromEpochDay와 validToEpochDay 생성
- buildNutritionPlan 함수에서 현재 체중, 목표 체중, 골격근량, 체지방률, 기초대사량, 목표 기간을 바탕으로 일일 영양 계획 계산
- BodyMeasurementDraft를 사용하여 별도 신체 측정값 저장 초안 생성
- bodyFatPercentFromMass 함수로 체중과 체지방량을 이용한 체지방률 자동 계산
- 최신 BodyMeasurementEntity를 Current Profile에 적용하는 Use Latest Body Status 흐름 추가
- Manual Override 스위치로 직접 목표 입력 필드 표시 여부 제어
- GoalProgressOverview 컴포저블로 active goal 요약 화면 구성
- buildGoalProposal 함수로 저장 전 GoalPlanDraft 제안 생성
- estimateSkeletalMuscleMass, estimateBodyFatPercent, suggestTargetMuscleMass 함수로 비어 있는 신체 구성 값 추정
- GoalProposalCard에서 AI 제안값과 Estimated 항목, Confirm Goal 버튼 표시

구현된 내용:
- Start Date 필수 입력
- Target Date / Duration 모드 선택
- Target Date 모드: 목표 날짜 직접 입력
- Duration 모드: 목표 주차 입력 후 목표 날짜 자동 계산
- 현재 체중 필수 입력
- 현재 골격근량, 현재 기초대사량, 현재 체지방률 선택 입력
- Input Current Body Status 버튼으로 현재 몸 상태 입력 폼 표시
- 측정일, 체중, 기초대사량, 골격근량, 체지방량, 체지방률 입력 가능
- 입력값 중 하나 이상만 있으면 body_measurements에 저장 가능
- 체중과 체지방량을 함께 입력하면 체지방률 자동 계산
- 저장된 최신 측정값을 Use Latest Body Status 버튼으로 목표 초안에 적용
- Body Status 저장 후 AI Nutrition Plan은 자동 갱신되지만, 최종 목표 저장은 AI Goal Proposal을 확인한 뒤 사용자가 Confirm Goal로 승인
- 목표 체중, 목표 골격근량, 목표 체지방률 입력
- AI Nutrition Plan 자동 계산
- Daily Targets 기본값은 AI Plan 사용
- Manual Override 활성화 시 칼로리/탄단지/식이섬유/당/나트륨 직접 수정 가능
- active goal이 있는 경우 Goals 화면에서 목표 요약을 먼저 표시
- Input Current Body Status 버튼을 Edit Goal 버튼보다 위에 배치
- Goals 요약 화면에서도 Body Status 입력 폼을 열고 측정값 저장 가능
- Edit Goal 버튼 클릭 시 목표 편집 폼 표시
- Generate AI Goal Proposal 버튼으로 AI 목표 제안 생성
- 비어 있는 현재 골격근량, 현재 체지방률, 목표 체중, 목표 골격근량, 목표 체지방률은 AI 추정값으로 보완
- AI가 보완한 값은 Proposal 카드에서 Estimated로 표시
- Confirm Goal을 눌러야 GoalPlanDraft가 Repository로 전달되어 실제 저장
- Edit Details를 누르면 저장하지 않고 입력 폼으로 돌아가 다시 수정 가능

문제 해결 과정:
처음에는 Target Date와 Duration Weeks가 동시에 editable이어서 "8주 목표"와 "6주 뒤 목표 날짜"처럼 서로 충돌하는 입력이 가능했다. 이를 해결하기 위해 기간 설정의 source of truth를 하나만 선택하도록 변경하였다. Target Date 모드에서는 목표 날짜가 기준이고, Duration 모드에서는 주 단위 기간이 기준이다. 저장 시에는 어떤 모드였든 최종적으로 validFromEpochDay와 validToEpochDay만 DB에 저장한다.

Daily Targets도 AI Plan과 수동 입력값이 충돌할 수 있었다. 이를 해결하기 위해 기본 저장값은 AI Plan으로 통일하고, 사용자가 Manual Override를 켰을 때만 수동 목표값을 저장하도록 구분하였다. goal_plans의 plannerVersion에는 local-goal-planner-v1 또는 manual-override-v1을 저장하여 이후 목표 출처를 구분할 수 있게 하였다.

또한 인바디 측정값은 목표 저장과 완전히 같은 개념이 아니기 때문에, Current Profile 직접 입력 필드와 별도의 Body Status 입력 폼으로 분리하였다. 이 폼에서는 사용자가 모든 값을 입력하지 않아도 되도록 하여 실제 사용 상황에 맞췄다. 예를 들어 체중만 알거나 기초대사량만 알고 있는 경우에도 기록이 가능하다. 저장된 측정값은 즉시 목표 초안에 반영되지만, 실제 목표 계획은 AI Goal Proposal을 생성하고 Confirm Goal을 누를 때만 저장되도록 하여 AI가 자동으로 제안한 값을 사용자가 최종 확인할 수 있게 하였다.

목표가 이미 있는 사용자가 Goals 화면에 들어올 때 곧바로 편집 폼이 보이면 현재 목표가 잘 진행되고 있는지 확인하기 어렵다. 이를 해결하기 위해 active goal이 있으면 Current Goal, Body Progress, Daily Targets를 먼저 보여주고, Edit Goal은 명시적인 버튼으로 분리하였다. Body Status는 목표 수정과 별개로 자주 입력할 수 있는 값이므로, Input Current Body Status 버튼을 Edit Goal보다 위에 배치하여 현재 상태 기록 흐름을 더 빠르게 접근할 수 있도록 하였다.

골격근량이나 체지방률은 사용자가 항상 알고 있는 값이 아니기 때문에 빈칸이면 저장 자체를 막는 방식은 사용성을 떨어뜨린다. 대신 Generate AI Goal Proposal 단계에서 현재 체중, 목표 체중, 기간을 바탕으로 비어 있는 값을 추정하여 제안하고, Estimated 항목으로 표시하였다. 이 구조는 AI가 임의로 저장하는 것이 아니라 "초안 제안"을 만들고 사용자가 Confirm Goal로 승인하는 방식이므로, 편의성과 사용자 통제권을 동시에 확보할 수 있다.


4.3 목표 DB 및 저장 구조

13주차에는 목표 설정 값을 일회성 화면 상태가 아니라 Room DB에 저장하도록 변경하였다. 목표는 사용자가 중간에 수정할 수 있으므로 단순히 한 row를 덮어쓰면 안 된다. 특정 날짜의 식단 기록은 그 날짜에 적용되던 목표와 비교되어야 하기 때문에 목표는 기간을 가진 이력 데이터로 저장해야 한다.

추가된 Entity:
- GoalPlanEntity
- BodyMeasurementEntity

GoalPlanEntity 주요 필드:
- ownerId: 목표 계획을 소유한 사용자 id
- validFromEpochDay: 목표 적용 시작일
- validToEpochDay: 목표 적용 종료일 exclusive
- startWeightKg: 목표 시작 시점의 현재 체중
- startMuscleMassKg: 선택 입력한 현재 골격근량
- startBodyFatPercent: 선택 입력한 현재 체지방률
- targetWeightKg: 목표 체중
- targetMuscleMassKg: 목표 골격근량
- targetBodyFatPercent: 목표 체지방률
- dailyCalories, dailyCarbsGram, dailyProteinGram, dailyFatGram: 일일 탄단지 목표
- dailyFiberGram, dailySugarGram, dailySodiumMilligram: 건강 지표 목표
- planSummary: AI Plan 또는 Manual Override 요약
- plannerVersion: 목표 산출 방식

BodyMeasurementEntity 주요 필드:
- ownerId: 측정값을 소유한 사용자 id
- measuredEpochDay: 측정 날짜
- weightKg: 선택 입력한 현재 체중
- muscleMassKg: 선택 입력한 골격근량
- basalMetabolicRateKcal: 선택 입력한 기초대사량
- bodyFatMassKg: 선택 입력한 체지방량
- bodyFatPercent: 선택 입력하거나 체중/체지방량으로 계산된 체지방률

BodyMeasurementDraft 주요 역할:
- Body Status 입력 폼의 임시 저장 데이터 표현
- 하나 이상의 측정값이 입력되었는지 hasAnyValue로 검증
- GoalRepository.saveBodyMeasurement를 통해 목표 저장과 별도로 날짜별 측정값 저장

구현된 저장 흐름:
1. Goal Settings에서 Input Current Body Status 클릭
2. 측정일과 인바디 관련 값 입력
3. 날짜 형식과 최소 1개 이상 입력 여부 검증
4. BodyMeasurementDraft 생성
5. GoalRepository.saveBodyMeasurement 호출
6. body_measurements에 날짜별 측정값 insert
7. 입력된 측정값을 Current Profile 및 목표 초안에 자동 반영
8. 사용자가 Generate AI Goal Proposal 클릭
9. 시작일, 목표 종료일, 현재 체중 필수 검증
10. 비어 있는 현재/목표 골격근량, 체지방률, 목표 체중을 AI 추정값으로 보완
11. GoalPlanDraft를 포함한 GoalPlanProposal 생성
12. AI Goal Proposal 카드에 기간, 신체 목표, 일일 영양 목표, Estimated 항목 표시
13. 사용자가 Edit Details를 누르면 저장하지 않고 입력 폼으로 돌아감
14. 사용자가 Confirm Goal을 누르면 GoalRepository.saveGoalPlan 호출
15. 기존 목표 중 새 시작일과 겹치는 목표의 validToEpochDay를 새 시작일로 수정
16. 새 시작일 이후의 미래 목표 row 삭제
17. 새 GoalPlanEntity insert
18. 같은 날짜의 BodyMeasurementEntity insert

문제 해결 과정:
목표 수정 시 기존 목표를 단순 update하면 과거 식단 기록을 어떤 목표와 비교해야 하는지 알 수 없게 된다. 이를 해결하기 위해 목표를 "현재 값"이 아니라 "기간이 있는 이력"으로 저장하였다. 이렇게 하면 2026.05.25의 식단 기록은 2026.05.25에 유효했던 목표와 비교되고, 2026.05.30에 목표를 수정하면 그 이후 기록만 새 목표와 비교할 수 있다.

추가로 body_measurements는 목표 계획과 독립적으로 여러 번 기록될 수 있어야 한다. 사용자가 목표를 새로 저장하지 않아도 인바디 측정값만 기록할 수 있도록 saveBodyMeasurement를 별도로 두었다. 이렇게 하면 몸 상태 기록은 날짜별 로그로 남고, 목표 계획은 사용자가 최종 승인한 경우에만 goal_plans에 저장된다.


4.4 Home 화면

Home 화면은 기존에 targetCalories, targetProteinGram 등 일부 목표값을 AIDietNavHost의 rememberSaveable 상태에서 전달받았다. 13주차에는 active goal이 DB에 저장되어 있으면 해당 값을 우선 사용하도록 변경하였다.

구현 기술:
- GoalRepository.observeActiveGoalPlan(ownerId, todayEpochDay)로 오늘 날짜에 유효한 목표 관찰
- activeGoalPlan이 있으면 dailyCalories, dailyCarbsGram, dailyProteinGram, dailyFatGram, dailyFiberGram, dailySugarGram, dailySodiumMilligram 사용
- activeGoalPlan이 없으면 기존 기본값 사용

구현된 내용:
- 오늘 목표 칼로리 DB 기반 표시
- 탄수화물/단백질/지방 목표 DB 기반 표시
- 식이섬유/당/나트륨 목표 DB 기반 표시
- Goal Settings에서 저장한 목표가 Home 화면에 즉시 반영


4.5 Insights 화면

Insights 화면은 12주차에는 최근 식단 기록의 평균과 경향을 보여주는 수준이었다. 13주차에는 사용자별·시점별 목표와 식단 기록을 날짜 단위로 매칭하여, 실제 섭취량이 그날 적용되던 목표에 비해 어느 정도였는지 볼 수 있도록 변경하였다. 이후 화면을 더 간결하게 만들기 위해 Active Goal 카드는 제거하고, Calorie Trend와 Nutrition Trend를 날짜별 막대 목록이 아니라 라인 그래프로 표시하도록 개선하였다.

구현 기술:
- GoalRepository.observeGoalPlans(ownerId)로 전체 목표 이력 관찰
- mealRecords를 날짜별 DailyNutritionStats로 변환
- 각 날짜마다 goalPlans.goalFor(date)를 호출하여 해당 날짜의 목표 찾기
- CalorieTrendChart에서 최근 기록일의 실제 칼로리와 목표 칼로리를 Canvas 라인으로 표시
- NutritionTrendChart에서 탄수화물/단백질/지방을 목표 대비 비율로 변환하여 Canvas 라인으로 표시
- DrawScope.drawChartLine helper를 만들어 여러 라인 그래프에서 재사용
- ChartLegend와 ChartDateLabels를 분리하여 그래프 범례와 날짜 표시 재사용

구현된 내용:
- Active Goal 카드 제거
- Recent Day Averages 카드가 화면 상단에 바로 표시되도록 정리
- Calorie Trend를 실제 섭취 칼로리 라인과 목표 칼로리 라인으로 표시
- Nutrition Trend를 탄수화물, 단백질, 지방 목표 대비 비율 라인으로 표시
- Nutrition Trend에 100% 목표 기준선 표시
- 최근 기록일의 실제/목표 값을 Latest 문구로 표시
- 그래프 범례를 색상별로 제공하여 Intake, Goal, Carbs, Protein, Fat 구분
- 모바일 화면 폭에서 범례가 겹치지 않도록 2개씩 줄바꿈되는 레이아웃 적용

문제 해결 과정:
목표가 중간에 변경되면 하나의 최신 목표값으로 모든 과거 식단을 비교하는 것은 부정확하다. 예를 들어 5월 25일에는 1900 kcal 목표였고 5월 30일부터 2100 kcal 목표로 바꾸었다면, 5월 25일 식단은 1900 kcal 기준으로 비교되어야 한다. 이를 위해 goal_plans의 validFromEpochDay와 validToEpochDay를 사용하여 각 식단 날짜에 유효한 목표를 찾아 비교하도록 구현하였다.

기존 progress bar 방식은 날짜별 상세 값은 볼 수 있었지만, 전체 흐름을 한눈에 파악하기 어려웠다. 이를 해결하기 위해 최근 7개 기록일을 오래된 날짜에서 최신 날짜 순으로 정렬한 뒤, Canvas에 라인 그래프로 표시하였다. Calorie Trend는 절대 칼로리 값을 사용하고, Nutrition Trend는 탄수화물/단백질/지방의 단위와 목표값이 서로 다르기 때문에 목표 대비 비율로 정규화하여 한 그래프 안에서 비교할 수 있게 하였다.


4.6 Insights Body Progress 개선

13주차 추가 구현 과정에서 Insights 화면에 Body Progress 영역을 확장하였다. 사용자가 Goal Settings에서 입력한 Body Status 기록은 body_measurements에 누적 저장되며, Insights 화면에서는 최근 측정 기록을 이용해 체중, 골격근량, 체지방률 변화를 확인할 수 있도록 하였다.

구현 기술:
- GoalRepository.observeBodyMeasurements(ownerId)를 통해 사용자별 체성분 기록을 관찰
- RecentStatsScreen에 bodyMeasurements를 전달하여 Insights 화면에서 사용
- BodyProgressPanel 컴포저블 추가
- BodyMeasurementTrendChart에서 체중, 골격근량, 체지방률을 Canvas 라인 그래프로 표시
- BodyMeasurementRow에서 측정일별 체중, 골격근량, 기초대사량, 체지방량, 체지방률 요약 표시
- rememberSaveable을 이용하여 Body Progress 기록 목록의 펼침/접힘 상태 관리

구현된 내용:
- Body Progress 카드에 최신 Weight, Muscle, Body Fat 요약 칩 표시
- 최근 체성분 기록을 그래프로 시각화
- 기록 목록은 기본적으로 최근 3개만 표시
- 기록이 4개 이상이면 Show all records 버튼 표시
- 사용자가 버튼을 누르면 전체 기록을 펼쳐서 확인 가능
- 펼친 상태에서는 Show less 버튼으로 다시 최근 3개만 보이도록 접기 가능

문제 해결 과정:
체성분 기록은 사용자가 자주 입력할 수 있는 데이터이므로 모든 기록을 한 화면에 계속 노출하면 Insights 화면이 지나치게 길어지고, 칼로리/영양소 추세 그래프를 확인하기 어려워진다. 이를 해결하기 위해 기본 상태에서는 최근 기록 3개만 보여주고, 더 많은 기록은 사용자가 필요할 때만 펼쳐보는 방식으로 변경하였다. 이렇게 하면 최근 상태는 바로 확인할 수 있고, 과거 기록도 숨겨지는 것이 아니라 명시적인 버튼으로 접근할 수 있다.


4.7 식사 입력 UX 및 AI 분석 확인 흐름 개선

기존 Add Meal 화면은 사용자가 Food Name과 Description을 음식 항목별로 직접 입력하고, 여러 음식을 먹은 경우 Add Another Food 버튼을 눌러 항목을 추가해야 했다. 하지만 실제 식사는 김치찌개, 밥, 반찬처럼 여러 음식이 한 번에 섞여 있는 경우가 많고, 사용자가 한 입력칸에 여러 음식을 적으면 기존 구조에서는 하나의 음식으로 묶여 저장되는 문제가 있었다.

이를 해결하기 위해 신규 식사 입력 흐름을 AI 중심으로 단순화하였다. 사용자는 사진 1장과 자유 입력 텍스트 1개만 작성하면 되고, AI가 식사 안의 여러 음식을 분리하여 분석한다. 분석 결과는 바로 DB에 저장하지 않고, 사용자가 Review Meal 화면에서 확인한 뒤 Confirm Meal을 눌렀을 때만 저장되도록 변경하였다.

구현 기술:
- 신규 Add Meal 화면에서는 SingleMealCaptureScreen을 사용하여 사진 선택과 자유 입력 텍스트 1개만 제공
- 기존 음식별 입력 UI는 edit 모드에서만 유지하여 이미 저장된 음식 항목별 영양소 수정이 가능하도록 함
- GeminiMealAnalyzer prompt를 수정하여 사진과 텍스트에서 여러 음식을 distinct food item으로 분리하도록 지시
- 사진과 텍스트에 같은 음식이 중복 등장하면 같은 메뉴를 중복 저장하지 않고 하나로 합치도록 prompt와 repository 후처리 추가
- MealReviewRepository에서 AI가 반환한 foods 배열 전체를 MealFoodRecord 목록으로 변환
- AI가 실패한 경우에도 사용자가 입력한 텍스트를 쉼표, and, with, 그리고, 및 등으로 나누어 로컬 fallback 분리 시도
- normalizedFoodKey를 사용하여 음식명 중복 여부를 판단하고 중복 음식은 mergeWith로 병합
- AIDietNavHost에 PendingMealReviewState를 추가하여 분석 중/완료/실패 상태를 메모리에서 관리
- Routes에 MealReview route 추가
- MealReviewScreen을 새로 추가하여 분석 결과 확인, Confirm, Retry, Discard 흐름 제공
- HomeScreen에 MealAnalysisNoticeUiState와 분석 상태 카드 추가

구현된 내용:
- Add Meal 신규 등록 화면에서 Add Another Food 버튼 제거
- Food Name과 Description을 나누는 대신 Meal Description 하나로 입력 방식 단순화
- 사진을 첨부하지 않은 경우 큰 빈 이미지 placeholder를 표시하지 않고 Add Photo 버튼만 표시
- Analyze Meal 클릭 시 즉시 Home 화면으로 이동
- Home 화면에서 AI is analyzing your meal 상태 카드 표시
- 분석 완료 시 Meal analysis ready 카드와 Review Result 버튼 표시
- Review Meal 화면에서 AI가 분리한 음식 목록, 전체 칼로리, 탄수화물, 단백질, 지방, 식이섬유, 당, 나트륨 확인 가능
- Confirm Meal 클릭 시에만 Room DB에 식사 기록 저장
- Confirm 전에는 Home 화면의 오늘 섭취 칼로리와 영양소 합계에 반영되지 않음
- 분석 실패 시 Retry 또는 Discard 선택 가능
- Review Meal 화면에서도 사진이 없는 경우 큰 No meal photo attached placeholder를 표시하지 않도록 정리

문제 해결 과정:
식사 기록 앱에서 사용자가 여러 음식을 직접 항목별로 나누어 입력하도록 강제하면 사용성이 떨어진다. 특히 한식 식사는 밥, 국, 반찬이 함께 구성되기 때문에 사용자가 한 번에 적은 내용을 AI가 분리하는 방식이 앱의 목적에 더 적합하다. 따라서 신규 입력 화면은 자유 입력 중심으로 단순화하고, AI 분석 결과를 별도 Review 단계에서 확인하도록 변경하였다.

또한 AI 분석 결과를 즉시 저장하면 잘못 분리되거나 칼로리가 부정확한 경우 사용자가 수정할 기회를 갖기 어렵다. 이를 해결하기 위해 분석 완료 후 Review Meal 화면을 거치도록 하였다. 이 구조에서는 분석 중 상태와 분석 완료 상태가 Home에 표시되고, Confirm Meal을 누르기 전까지는 DB에 저장되지 않는다. 따라서 Home의 오늘 섭취량은 사용자가 확정한 기록만 반영한다.

사진과 텍스트를 함께 입력했을 때 같은 음식이 중복 저장되는 문제도 고려하였다. Gemini prompt에서 같은 음식은 한 번만 반환하도록 지시하고, Repository 레벨에서도 정규화된 음식명 key를 기준으로 중복을 한 번 더 병합하도록 하였다. 이중 방어 구조를 두어 AI 응답이 완벽하지 않아도 저장 단계에서 중복을 줄일 수 있게 하였다.


5. 데이터베이스 변경 사항

Room Database version을 6에서 7로 올리고 MIGRATION_6_7을 추가하였다. 이후 Body Status 입력 기능에서 기초대사량과 체지방량을 별도로 저장할 필요가 생겨 version을 8로 올리고 MIGRATION_7_8을 추가하였다.

추가된 테이블:
- goal_plans
- body_measurements

추가된 DAO:
- GoalDao.observeBodyMeasurements(ownerId)
- GoalDao.observeGoalPlans(ownerId)
- GoalDao.observeActiveGoalPlan(ownerId, epochDay)
- GoalDao.closeOverlappingGoalPlans(ownerId, newValidToEpochDay)
- GoalDao.deleteGoalPlansStartingAtOrAfter(ownerId, fromEpochDay)
- GoalDao.insertGoalPlan(goalPlan)
- GoalDao.insertBodyMeasurement(bodyMeasurement)

추가된 Repository:
- GoalRepository.observeBodyMeasurements(ownerId)
- GoalRepository.observeGoalPlans(ownerId)
- GoalRepository.observeActiveGoalPlan(ownerId, epochDay)
- GoalRepository.saveBodyMeasurement(ownerId, draft)
- GoalRepository.saveGoalPlan(ownerId, draft)

Migration 변경:
- MIGRATION_6_7: goal_plans, body_measurements 테이블 최초 추가
- MIGRATION_7_8: body_measurements의 weightKg를 nullable로 변경하고 basalMetabolicRateKcal, bodyFatMassKg 필드 추가
- 기존 body_measurements 데이터를 body_measurements_new로 복사한 뒤 테이블을 교체하여 기존 측정 기록 보존


6. 검증 결과

현재 로컬 구현 기준으로 다음 명령을 실행하였다.

- JAVA_HOME="/Applications/Android Studio.app/Contents/jbr/Contents/Home" ./gradlew assembleDebug
- 실행 결과: BUILD SUCCESSFUL

처음에는 시스템 Java Runtime을 찾지 못해 Gradle이 실행되지 않았다.

The operation couldn't be completed. Unable to locate a Java Runtime.

이를 해결하기 위해 Android Studio에 포함된 JBR 경로를 JAVA_HOME으로 지정한 뒤 assembleDebug를 다시 실행하였다. 결과적으로 Compose 컴파일, KSP, 리소스 처리, APK 패키징까지 정상 완료되어 현재 로컬 구현은 디버그 빌드 기준으로 검증되었다.
