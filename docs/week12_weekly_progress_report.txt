2. 12주차 개발 목표

12주차의 핵심 목표는 11주차에 만든 화면과 데이터 설계를 실제 사용자 입력 데이터와 연결하는 것이었다. 기존에는 화면에서 sampleMeals 샘플 데이터를 사용했기 때문에 앱을 실행할 때마다 미리 만들어 둔 식단 기록만 표시되었다. 이번 주에는 사용자가 음식 추가 화면에서 입력한 정보와 선택한 이미지를 Room Database에 저장하고, 홈 화면, 식단 기록 화면, 상세 화면, 통계 화면이 DB 데이터를 기준으로 동작하도록 수정하였다.

주요 목표는 다음과 같다.

- Room.databaseBuilder를 사용하여 실제 MealDatabase 인스턴스 생성
- MealRepository와 MealDao를 통해 Room DB 저장/조회 흐름 연결
- AddMealScreen에서 입력한 음식명, 설명, 이미지 URI를 MealUploadDraft로 변환
- 저장 버튼 클릭 시 AI/로컬 검수 과정을 거쳐 MealRecord로 저장
- MealListScreen에서 sampleMeals 대신 Room DB Flow 데이터를 표시
- MealDetailScreen에서 저장된 실제 기록의 상세 정보 표시
- 이미지 선택 기능 구현 및 선택한 이미지 미리보기 표시
- 선택한 이미지 URI를 MealRecord 및 MealFoodRecord에 저장
- 실제 AI 분석을 위해 Firebase AI Gemini 모듈 추가
- AI 분석 실패 시에도 앱이 동작하도록 로컬 영양 추정 fallback 구현
- 로그인/회원가입 및 사용자별 식단 기록 분리 구조 추가

4. 화면별 구현 내용

4.1 로그인 및 회원가입 화면

12주차에는 기존 프로필 수정 UI와 별도로 앱 시작 시 사용할 로그인/회원가입 화면을 추가하였다. 사용자는 아이디와 비밀번호를 입력하여 로그인할 수 있고, 계정이 없으면 회원가입 모드로 전환하여 아이디, 닉네임, 비밀번호를 등록할 수 있다.

구현 기술:
- LoginScreen에서 rememberSaveable로 입력 상태 관리
- Room DB의 UserAccount Entity를 사용하여 계정 저장
- AuthDao, AuthRepository를 통한 계정 조회, 등록, 수정
- SHA-256 해시를 사용하여 비밀번호 원문 대신 passwordHash 저장
- AuthSessionStore에서 SharedPreferences로 현재 로그인 사용자 id 저장
- AIDietNavHost에서 저장된 사용자 id를 복원하고 시작 화면을 Login 또는 Home으로 분기

구현된 내용:
- 로그인 입력 검증
- 회원가입 입력 검증
- 중복 아이디 확인
- 로그인 실패 메시지 표시
- 회원가입 성공 시 바로 홈 화면 이동
- 앱 재실행 시 기존 로그인 세션 복원
- 로그아웃 시 세션 삭제 후 로그인 화면 이동

문제 해결 과정:
처음 계획에는 Firebase Auth나 소셜 로그인을 제외하기로 했기 때문에, 복잡한 인증 시스템 대신 로컬 DB 기반의 간단한 계정 구조를 만들었다. 다만 사용자별 식단 기록을 분리하려면 최소한의 사용자 식별자가 필요했다. 이를 해결하기 위해 UserAccount 테이블을 추가하고, 각 MealRecord에 ownerId를 저장하도록 설계하였다. 이렇게 하면 같은 앱 안에서도 로그인한 사용자에 따라 서로 다른 식단 기록을 조회할 수 있다.


4.2 홈 화면

홈 화면은 11주차에는 sampleMeals를 기준으로 오늘의 칼로리와 영양소를 계산했다. 12주차에는 AIDietNavHost에서 Room DB Flow를 collectAsState로 관찰하고, HomeScreen에 실제 저장된 mealRecords 리스트를 전달하도록 변경하였다.

구현 기술:
- mealRepository.observeMealRecords(currentUserId)로 사용자별 식단 기록 Flow 관찰
- collectAsState(initial = emptyList())로 Compose 상태 변환
- isTodayMeal(createdAt)로 오늘 기록 필터링
- MealRecord의 계산 프로퍼티를 이용하여 칼로리와 영양소 합계 계산
- 탄수화물, 단백질, 지방, 식이섬유, 당, 나트륨 요약 표시

구현된 내용:
- 오늘 섭취 칼로리 표시
- 목표 칼로리 대비 남은 칼로리 표시
- 칼로리 진행률 표시
- 탄수화물, 단백질, 지방 막대 표시
- 식이섬유, 당, 나트륨 건강 지표 표시
- History, Add, Goals, Insights, Profile 화면 이동

문제 해결 과정:
샘플 데이터 기반 UI에서는 앱을 새로 실행해도 같은 기록이 보였지만, 사용자가 입력한 데이터가 반영되지 않았다. 이를 해결하기 위해 데이터 출처를 sampleMeals에서 Room DB Flow로 변경했다. 또한 사용자가 로그인하지 않은 상태에서는 빈 리스트를 반환하도록 flowOf(emptyList())를 사용하여 비로그인 상태에서도 화면 데이터 흐름이 깨지지 않게 처리하였다.


4.3 음식 추가 화면

음식 추가 화면은 이번 주에 가장 크게 바뀐 화면이다. 11주차에는 음식명, 칼로리, 메모 입력과 Mock AI 분석 흐름이 중심이었다. 12주차에는 사용자가 여러 음식 항목을 추가하고, 각 항목마다 음식명, 설명, 사진을 입력한 뒤 AI 분석을 통해 영양 정보를 생성하는 방식으로 개선하였다.

구현 기술:
- mutableStateListOf로 여러 FoodDraftUiState 관리
- ActivityResultContracts.OpenDocument로 이미지 선택
- contentResolver.takePersistableUriPermission으로 선택 이미지 접근 권한 유지
- UriImage 공통 컴포넌트로 선택 이미지 미리보기
- MealUploadDraft, MealFoodDraft를 이용해 저장 전 초안 데이터 구성
- onSaveClick에서 MealReviewRepository.reviewMealDraft 호출
- 저장 중에는 버튼 텍스트를 Analyzing...으로 표시하고 중복 저장 방지

구현된 내용:
- 한 끼에 여러 음식 항목 추가 가능
- Food 1, Food 2 형태로 음식 항목 구분
- 각 음식별 음식명 입력
- 각 음식별 상세 설명 입력
- 각 음식별 사진 추가/변경/삭제
- 모든 항목이 비어 있으면 저장하지 않는 입력 검증
- 새 기록 저장 시 MealList 화면으로 이동
- 기존 기록 수정 시 Edit Meal 화면에서 저장 후 이전 화면 복귀

문제 해결 과정:
처음에는 음식 하나만 저장하는 구조였지만, 실제 식사는 여러 음식으로 구성되는 경우가 많다. 예를 들어 "밥 + 국 + 반찬"처럼 한 끼 안에 여러 항목을 기록해야 영양 정보가 더 자연스럽게 계산된다. 이를 해결하기 위해 MealRecord 하나에 여러 MealFoodRecord가 포함되도록 데이터 구조를 바꾸고, UI에서도 Add Another Food 버튼을 추가하였다.

또한 이미지 선택 후 상세 화면이나 리스트 화면에서 이미지를 계속 표시하려면 단순 URI 문자열 저장만으로는 부족할 수 있다. Android 문서 선택기에서 받은 URI에 대해 지속 읽기 권한을 요청하여 앱이 다시 실행되거나 DB에서 다시 불러와도 이미지에 접근할 수 있도록 처리하였다.


4.4 식단 기록 리스트 화면

식단 기록 리스트 화면은 11주차에 LazyColumn과 Today/All 필터가 구현되어 있었다. 12주차에는 리스트의 데이터 출처를 sampleMeals에서 Room DB 데이터로 변경하였다.

구현 기술:
- MealListScreen은 mealRecords: List<MealRecord>를 전달받아 표시
- AIDietNavHost에서 DB Flow를 관찰한 결과를 MealListScreen으로 전달
- Today 필터는 isTodayMeal(createdAt) 기준으로 동작
- All Records 필터는 사용자 DB에 저장된 전체 기록 표시
- UriImage로 대표 이미지 표시
- 각 기록 카드를 클릭하면 mealDetail/{mealId}로 이동

구현된 내용:
- 오늘 기록 보기 필터
- 전체 기록 보기 필터
- 저장된 기록이 없을 때 빈 상태 메시지 표시
- 음식명, 날짜/시간, 칼로리, 탄단지, 식이섬유, 당, 나트륨 표시
- 대표 이미지 표시
- 리스트 항목 클릭 시 상세 화면 이동

문제 해결 과정:
Room DB는 비동기로 데이터를 제공하기 때문에, 화면이 처음 그려질 때 데이터가 비어 있을 수 있다. 이를 자연스럽게 처리하기 위해 collectAsState(initial = emptyList())를 사용하고, 리스트 화면에는 빈 상태 메시지를 남겨 사용자가 저장된 기록이 없는 상황을 이해할 수 있도록 했다.


4.5 식단 상세 및 수정 화면

상세 화면은 저장된 기록의 내용을 한 화면에서 확인하는 역할을 한다. 12주차에는 상세 화면이 실제 DB 기록을 기준으로 동작하도록 변경되었고, 상세 화면에서 수정 화면으로 이동할 수 있는 기능도 추가되었다.

구현 기술:
- mealDetail/{mealId} route로 상세 기록 식별
- mealRecords.firstOrNull { it.id == mealId }로 현재 DB 목록에서 기록 검색
- editMeal/{mealId} route 추가
- AddMealScreen을 재사용하여 수정 화면 구현
- MealRepository.updateMealRecord에서 기존 음식 항목 삭제 후 새 음식 항목 삽입

구현된 내용:
- 대표 음식 이미지 표시
- 음식명, 기록 시간, 총 칼로리, 메모 표시
- 음식 항목별 칼로리와 영양소 표시
- 전체 탄수화물, 단백질, 지방, 식이섬유, 당, 나트륨 표시
- AI가 추정한 음식명, 칼로리, 요약 문구 표시
- 수정 버튼 표시
- 수정 화면에서 기존 음식명, 설명, 이미지 URI 복원

문제 해결 과정:
식단 수정 기능에서는 기존 MealRecord의 id를 유지하면서 음식 항목 목록은 다시 저장해야 했다. 음식 항목은 별도 테이블인 meal_foods에 저장되므로, 업데이트 시 meals 테이블을 갱신한 뒤 기존 meal_foods를 삭제하고 새 항목을 삽입하는 방식으로 처리하였다. 이 작업이 중간에 끊기면 데이터가 불일치할 수 있으므로 MealRepository에서 withTransaction을 사용하여 하나의 트랜잭션으로 묶었다.


4.6 최근 통계 화면

최근 통계 화면은 기존에 샘플 데이터를 날짜별로 그룹화하여 평균과 경향을 계산했다. 12주차에는 같은 계산 로직을 실제 DB 기록 리스트에 적용하도록 변경하였다.

구현 기술:
- mealRecordDate(createdAt) 기준으로 날짜별 groupBy
- 최근 7개 기록일 기준 통계 계산
- 평균 칼로리, 평균 단백질, 평균 기록 수 계산
- 최신 기록일과 직전 기록일의 칼로리 차이 비교
- LinearProgressIndicator로 칼로리 및 단백질 목표 진행률 표시

구현된 내용:
- 최근 기록일 평균 표시
- 칼로리 평균 표시
- 단백질 평균 표시
- 기록 개수 평균 표시
- 직전 기록일 대비 섭취 칼로리 변화 문구 표시
- 날짜별 칼로리 경향 표시
- 날짜별 탄수화물, 단백질, 지방 경향 표시

문제 해결 과정:
통계 화면은 데이터 출처가 sampleMeals에서 DB로 바뀌어도 계산 방식 자체는 유지될 수 있게 구성되어 있었다. 그래서 이번 주에는 화면 내부 계산 함수를 크게 바꾸지 않고, 상위 NavHost에서 전달하는 mealRecords만 DB 기반으로 교체하였다. 이 방식 덕분에 UI와 계산 로직을 재사용하면서 실제 저장 데이터 기반 통계로 전환할 수 있었다.


4.7 목표 설정 및 프로필 화면

목표 설정 화면은 현재 체중, 목표 체중, 목표 기간, 하루 목표 칼로리, 단백질 목표를 입력하는 구조를 유지하였다. 12주차에는 목표 칼로리와 단백질 목표가 DB 기반 식단 기록과 함께 홈 화면 및 통계 화면에서 계산에 사용되도록 연결 상태를 유지하였다.

프로필 화면은 로그인 계정 정보와 연결되도록 개선하였다. 닉네임, 아이디, 새 비밀번호를 수정할 수 있고, 저장 시 AuthRepository.updateProfile을 통해 DB의 UserAccount가 갱신된다. 비밀번호 입력란을 비워 두면 기존 비밀번호 해시를 유지하도록 처리하였다.

구현된 내용:
- 프로필 닉네임 수정
- 아이디 수정
- 새 비밀번호 설정
- 중복 아이디 검증
- 로그아웃 기능
- 목표 칼로리와 단백질 목표를 홈/통계 화면에 반영

현재 한계:
목표 설정 값은 아직 별도 DB 테이블에 영구 저장되지 않고 AIDietNavHost의 rememberSaveable 상태로 관리된다. 13주차 이후에는 목표 설정 값도 사용자별로 저장하는 구조를 추가할 수 있다.


5. 데이터 구조 및 저장 구현

12주차에는 Room Database 설계가 실제 저장 구조로 확장되었다. 기존에는 MealRecord 중심의 단일 식단 데이터 모델을 계획했지만, 이번 주에는 한 끼 식사 안에 여러 음식 항목을 저장할 수 있도록 meals 테이블과 meal_foods 테이블을 분리하였다.

주요 Entity:

- UserAccount: 사용자 계정 정보 저장
- MealEntity: 한 끼 식사 기록의 대표 정보 저장
- MealFoodEntity: 한 끼 식사에 포함된 개별 음식 항목 저장

MealEntity 주요 필드:
- id: 식단 기록 고유 번호
- ownerId: 식단 기록을 소유한 사용자 id
- memo: 식단 메모
- imageUri: 대표 이미지 URI
- aiSummary: AI 분석 요약
- createdAt: 기록 생성 시간

MealFoodEntity 주요 필드:
- id: 음식 항목 고유 번호
- mealId: 연결된 식단 기록 id
- foodName: 음식명
- description: 사용자가 입력한 설명
- imageUri: 음식 항목 이미지 URI
- calories: 칼로리
- carbsGram: 탄수화물 g
- proteinGram: 단백질 g
- fatGram: 지방 g
- fiberGram: 식이섬유 g
- sugarGram: 당 g
- sodiumMilligram: 나트륨 mg
- aiFoodName: AI가 추정한 음식명
- aiCalories: AI가 추정한 칼로리
- confidence: AI 또는 로컬 추정 신뢰도

MealDao 구현 내용:
- observeMealRecords(ownerId): 특정 사용자의 전체 식단 기록을 최신순으로 Flow 관찰
- getMealRecord(mealId, ownerId): 특정 사용자의 단일 식단 기록 조회
- insertMeal: 식단 대표 정보 저장
- updateMeal: 식단 대표 정보 수정
- insertMealFoods: 음식 항목 목록 저장
- deleteMealFoods: 특정 식단의 음식 항목 삭제
- deleteMeal: 식단 기록 삭제

MealRepository 구현 내용:
- observeMealRecords에서 MealWithFoods를 MealRecord로 변환
- addMealRecord에서 MealEntity 삽입 후 반환된 mealId를 사용하여 음식 항목 저장
- updateMealRecord에서 트랜잭션으로 식단 대표 정보와 음식 항목 목록 갱신
- deleteMealRecord에서 식단 삭제

문제 해결 과정:
Room에서 1:N 관계를 표현하기 위해 MealEntity와 MealFoodEntity를 분리하고, MealWithFoods에 @Embedded와 @Relation을 사용하였다. 이렇게 하면 DB에는 정규화된 형태로 저장하면서, 화면에서는 MealRecord 하나로 합쳐진 데이터를 사용할 수 있다. UI 입장에서는 mealRecord.foods로 음식 목록을 바로 사용할 수 있어 코드가 더 자연스러워졌다.


6. 이미지 선택 및 표시 구현

12주차에는 과제 요구사항 중 "이미지 포함"을 실제 기능으로 구현하였다.

구현 기술:
- ActivityResultContracts.OpenDocument 사용
- imagePicker.launch(arrayOf("image/*"))로 이미지 문서 선택기 실행
- 선택된 Uri를 문자열로 변환하여 FoodDraftUiState와 MealFoodDraft에 저장
- contentResolver.takePersistableUriPermission으로 지속 읽기 권한 요청
- UriImage 컴포넌트에서 contentResolver.openInputStream으로 이미지 로드
- BitmapFactory.decodeStream과 asImageBitmap으로 Compose Image 표시

구현된 내용:
- 음식 추가 화면에서 사진 선택 가능
- 선택된 사진 미리보기 표시
- 사진 변경 가능
- 사진 제거 가능
- 리스트 화면에서 대표 사진 표시
- 상세 화면에서 대표 사진 크게 표시
- 사진을 불러오지 못하는 경우 placeholder 텍스트 표시

문제 해결 과정:
이미지 URI는 일반 문자열처럼 저장할 수 있지만, 앱이 나중에 다시 해당 URI에 접근하려면 권한 문제가 생길 수 있다. 이를 해결하기 위해 OpenDocument를 사용하고 persistable read permission을 요청하였다. 또한 이미지 표시 코드를 여러 화면에서 반복하지 않도록 UriImage 컴포넌트를 분리하여 음식 추가, 리스트, 상세 화면에서 재사용하였다.


7. AI 분석 및 로컬 영양 추정 구현

11주차에는 Mock AI 분석 버튼만 있었다. 12주차에는 Firebase AI SDK를 추가하고, Gemini 기반 분석 모듈을 구현하였다. 사용자가 사진과 음식 설명을 입력하면 GeminiMealAnalyzer가 이미지와 텍스트를 함께 전송하고, JSON 형식의 영양 분석 결과를 받아온다.

구현 기술:
- Firebase AI SDK 추가
- Google Services Gradle Plugin 추가
- google-services.json 설정 파일 추가
- AndroidManifest.xml에 INTERNET permission 추가
- GeminiMealAnalyzer에서 gemini-2.5-flash 모델 사용
- 이미지 URI를 Bitmap으로 로드하고 최대 크기 기준으로 샘플링
- Gemini 응답에서 JSON 객체를 추출하여 JSONObject로 파싱
- MealAiAnalysis, MealAiFoodAnalysis 데이터 클래스로 결과 표현
- MealReviewRepository에서 AI 분석 결과를 MealRecord로 변환
- AI 분석 실패 시 estimateCaloriesFromFoodName, estimateMacros, estimateHealthMetrics 사용

구현된 내용:
- 음식 사진 기반 음식명 추정
- 음식 설명 기반 칼로리와 영양소 추정
- 탄수화물, 단백질, 지방 추정
- 식이섬유, 당, 나트륨 추정
- AI 요약 문구 저장
- AI 분석 실패 시 로컬 추정 결과 저장
- AI 또는 로컬 추정 신뢰도 저장

문제 해결 과정:
외부 AI API는 네트워크 상태, Firebase 설정, 응답 형식 문제로 실패할 수 있다. AI 분석 실패가 곧 식단 저장 실패로 이어지면 사용자가 기록을 남기지 못하는 문제가 생긴다. 이를 해결하기 위해 MealReviewRepository에서 runCatching으로 AI 분석을 감싸고, 결과가 없을 때는 로컬 추정 로직을 사용하도록 만들었다. 이 구조 덕분에 Gemini가 동작하지 않는 환경에서도 앱의 핵심 기능인 식단 저장은 계속 가능하다.

또한 Gemini가 항상 정확한 JSON만 반환한다고 보장할 수 없기 때문에, 응답 문자열에서 첫 번째 JSON 객체 부분을 추출한 뒤 JSONObject로 파싱하도록 처리하였다. 프롬프트에는 "Return JSON only"를 명시하여 응답 형식을 최대한 안정적으로 유도하였다.

10. 12주차 문제 해결 과정 요약

이번 주 개발에서 해결한 주요 문제는 다음과 같다.

1. 샘플 데이터에서 실제 DB 데이터로 전환
11주차에는 sampleMeals를 사용했기 때문에 사용자가 새로 입력한 데이터가 앱에 남지 않았다. 12주차에는 MealDatabase, MealRepository, Flow 관찰 구조를 실제 화면과 연결하여 저장된 기록이 홈, 리스트, 상세, 통계 화면에 반영되도록 변경하였다.

2. 한 끼 식사와 여러 음식 항목의 관계 정리
처음에는 하나의 MealRecord에 음식 하나만 저장하는 방식이 단순했지만, 실제 식사는 여러 음식으로 구성된다. 이를 해결하기 위해 meals와 meal_foods 테이블을 분리하고, @Relation으로 다시 합쳐서 화면에 전달하는 구조를 만들었다.

3. 이미지 URI 권한 문제 처리
이미지 선택 기능은 단순히 URI를 받는 것만으로는 충분하지 않다. 앱이 나중에 DB에서 URI를 다시 읽을 때 권한이 사라질 수 있기 때문이다. OpenDocument와 takePersistableUriPermission을 사용하여 지속 접근 권한을 확보하였다.

4. AI 분석 실패 시 저장 불가 문제 방지
Gemini 분석은 네트워크나 응답 파싱 문제로 실패할 수 있다. 저장 기능이 AI에 완전히 의존하면 사용자가 기록을 남기지 못할 수 있으므로, AI 분석을 runCatching으로 감싸고 실패 시 로컬 추정 함수를 사용하도록 했다.

5. 수정 기능의 데이터 일관성 확보
식단 기록을 수정할 때 meals와 meal_foods를 따로 갱신하면 중간 실패 시 데이터가 꼬일 수 있다. 이를 해결하기 위해 MealRepository.updateMealRecord에서 withTransaction을 사용하여 대표 식단 정보와 음식 항목 갱신을 하나의 작업으로 묶었다.

6. 사용자별 기록 분리
로그인 기능을 추가하면서 모든 사용자가 같은 식단 기록을 보는 문제가 생기지 않도록 ownerId를 MealEntity에 추가했다. observeMealRecords(ownerId) 쿼리로 현재 로그인 사용자 기록만 조회하도록 구현하였다.


11. 현재 한계점

12주차 보고서 초안 작성 시점 기준으로 아직 완성되지 않은 부분은 다음과 같다.

- 목표 설정 값은 아직 Room DB에 영구 저장되지 않음
- 식단 기록 삭제 버튼은 Repository에는 있지만 UI에는 아직 연결되지 않음
- AI 분석 결과를 저장 전에 사용자가 직접 세부 수정하는 화면은 아직 없음
- Gemini 분석은 Firebase 설정과 네트워크 상태에 의존함
- 일부 화면 문구가 한국어와 영어가 섞여 있어 최종 제출 전 정리 필요
- 실제 앱 화면 스크린샷은 아직 docs/screenshots 폴더에 첨부되어 있지 않음
- 12주차 GitHub 커밋 수와 커밋 히스토리 그래프는 주말 추가 커밋 이후 제출 전 최종 업데이트 필요


12. 스크린샷 첨부 계획

12주차 보고서 제출 시 다음 화면을 캡처하면 구현 내용을 잘 보여줄 수 있다.

1. 로그인/회원가입 화면
2. 홈 화면: DB 기록 기준 오늘 칼로리와 영양소 요약
3. 음식 추가 화면: 여러 음식 항목, 이미지 선택 버튼, 설명 입력
4. 이미지 선택 후 미리보기 화면
5. 식단 기록 리스트 화면: Today/All Records 필터와 저장된 기록
6. 식단 상세 화면: 이미지, 음식 목록, 영양분 구성, AI 분석 기록
7. 최근 통계 화면: 칼로리 경향과 영양 경향
8. GitHub 커밋 히스토리 그래프


13. 빌드 및 테스트 확인

현재 코드 상태에서 Android Studio 내장 JDK를 사용하여 다음 Gradle 명령을 실행했을 때 성공적으로 완료되었다.

- ./gradlew testDebugUnitTest
- ./gradlew assembleDebug

이를 통해 12주차 구현 코드가 컴파일 가능하며, 기본 단위 테스트와 debug APK 조립이 가능한 상태임을 확인하였다.


14. 13주차 구현 예정 내용

13주차에는 12주차에서 구현한 실제 저장/조회/이미지/AI 분석 흐름을 안정화하고, 사용자 경험을 개선할 예정이다.

구현 예정 기능은 다음과 같다.

- AI 분석 결과를 저장 전에 사용자가 확인하고 수정할 수 있는 UI 추가
- 식단 기록 삭제 기능 UI 연결
- 목표 설정 값을 사용자별로 Room DB에 저장
- 화면 문구의 한국어/영어 혼용 정리
- AddMealScreen의 입력 흐름 개선
- Gemini 분석 실패/로딩/성공 상태를 더 명확히 표시
- 앱 주요 화면 스크린샷 정리
- README와 보고서 문서 보강
- GitHub 커밋을 기능 단위로 나누어 주차별 커밋 이력 보강

13주차의 핵심 목표는 "실제 저장되는 식단 기록 앱"에서 한 단계 더 나아가, 사용자가 AI 추정 결과를 신뢰하고 수정할 수 있는 완성도 높은 식단 기록 흐름을 만드는 것이다.
